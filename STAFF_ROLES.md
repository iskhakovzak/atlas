# Роли сотрудников и доступ в управление (RBAC)

Доступ к `/admin`, `/operations`, `/analytics` и к служебным API определяется ролью сотрудника из справочника команды (`market_staff_directory`). Карта прав — `lib/market/access.ts`, серверная проверка — `accessFor()` / `requirePermission()` в `lib/market/server.ts`. Браузеру не доверяем: права вычисляются на сервере при каждом запросе.

## Кто получает доступ

1. **Основной администратор** — адрес из секрета хостинга `ATLAS_OPERATOR_EMAIL`. Всегда роль `admin`, всегда активен; его карточка в справочнике не может быть понижена или отключена (сервер принудительно сохраняет `admin`/`active`).
2. **Сотрудник из справочника** — строка `market_staff_directory` с email пользователя (сравнение без учёта регистра), статус `active` и известная роль.

Условие для обоих: сессия должна быть создана **входом с подтверждённым email** — код на почту, Google или Apple. Вход по телефону или Telegram не несёт email и прав не даёт, даже если это тот же человек. Чтобы сотрудник работал под одним аккаунтом с телефоном, он может привязать способ входа в кабинете, но в управление входит именно через email-способ.

Статусы `invited` и `disabled` доступа не дают: карточка хранится для истории и приглашения.

## Роли и права

| Право | admin | finance | support | procurement | warehouse |
|---|:-:|:-:|:-:|:-:|:-:|
| `operations.read` — очередь заказов и клиенты (просмотр) | ✓ | ✓ | ✓ | ✓ | ✓ |
| `operations.act` — действия с заказами в очереди | ✓ | | | ✓ | ✓ |
| `catalog.manage` — каталог, импорт, подборки, публикация | ✓ | | | ✓ | |
| `pricing.manage` — тарифы, услуги, обновление курса | ✓ | | | | |
| `policy.manage` — лимиты и запрещённые категории | ✓ | | | | |
| `staff.manage` — справочник команды, роли и статусы | ✓ | | | | |
| `customers.manage` — статус клиента (см. ограничение ниже) | ✓ | | ✓ | | |
| `support.reply` — ответы в обращениях и уведомления клиенту | ✓ | | ✓ | | |
| `finance.read` — бухгалтерия, аналитика, CSV | ✓ | ✓ | | | |
| `finance.write` — записи журнала, аннулирование, настройки учёта | ✓ | ✓ | | | |
| `system.manage` — синхронизация базы, экспорт резервной копии, ошибки сервера | ✓ | | | | |
| `audit.read` — журнал действий | ✓ | ✓ | | | |

Решения:
- **support и статус клиента:** поддержка переводит клиента в «На проверке» и обратно в «Активен»; «Заблокирован» ставит только администратор (`err_51`). Это выбрано вместо отдельного права, чтобы не плодить ключи.
- **finance** видит очередь только для чтения (сверка заказов с книгами) и журнал действий; действий с заказами нет.
- **admin** — единственная роль с тарифами, правилами, командой и системными инструментами. Сотрудник с ролью `admin` равен основному администратору по правам (`operator: true`), но изменить основного администратора не может.

## Действия с заказами (`POST /api/operations`, `kind: "action"`)

| Действие | Право | Роли (кроме admin) |
|---|---|---|
| `advance`, `confirm-store-shipping`, `change-request-create`, `order-issue-update` | `operations.act` | procurement |
| `receive`, `parcel-set`, `warehouse-inspect`, `warehouse-service-complete`, `warehouse-service-decline` | `operations.act` | warehouse, procurement |
| `order-image`, `assign-order`, `staff-note` | `operations.act` | warehouse, procurement |
| `support-reply`, `customer-notification` | `support.reply` | support |

Клиентские действия (`cancel`, `approve-extra`, `checkout`, оплата…) оператору недоступны вовсе (`err_18`). Действие без нужного права или роли — `403 err_50`.

Остальные запросы: `pricing`/`fx-refresh` → `pricing.manage`; `policy` → `policy.manage`; `staff` и `staff-deactivate` (отключение с причиной; себя — `err_55`, основного администратора — `err_56`) → `staff.manage`; `customer-status` и `customer-note` (заметка о клиенте, таблица `market_customer_notes`, миграция 0011; без таблицы — `err_57`) → `customers.manage`; `projection-rebuild` и `admin-settings` (пороги «Требуют внимания», `market_settings` key `admin`) → `system.manage`. Секции `GET /api/operations` по запросу: `?audit=1&page=&actor=&entity=&from=&to=&q=` и `?audit=csv` → `audit.read`; `?customers=csv` (контакты и суммы, без паспортных данных и адресов) и `?customer=<id>` (карточка: заказы, обращения, заметки, получатели без адресов) → `customers.manage`; `?system=1` (состояние D1, курс, проекция, тариф, бэкап) → `system.manage`. Каждый экспорт и каждая запись фиксируются в журнале (`audit.export`, `customers.export`, `customer.note`, `staff.deactivate`, `admin.settings`). `GET /api/operations` требует `operations.read`; разделы ответа отдаются по правам (список сотрудников и их последние входы — `staff.manage`, журнал — `audit.read`, ошибки/vitals/предупреждения настройки — `system.manage`; без права приходят пустые значения). Дашборд `dashboard` (KPI, воронка, «Требуют внимания») считается на сервере (`lib/market/admin-server.ts`, чистые функции в `lib/market/admin-dashboard.ts`); пункты «Требуют внимания» обрезаются по правам зрителя (`attentionKindPermissions`: заказы и корзины — `operations.read`, обращения — `support.reply`, курс — `pricing.manage`, каталог — `catalog.manage`, приглашённые сотрудники — `staff.manage`). `GET /api/catalog?admin=1` и `POST /api/catalog` → `catalog.manage`. `GET /api/backup` → `system.manage` (экспорт включает все таблицы, в том числе документы личности).

Страницы: `/operations` — `operations.read`; `/analytics` — `finance.read`; `/admin` открывается любому активному сотруднику, вкладки фильтруются по правам (`adminTabPermissions`; вкладка «Контент сайта» — `content.manage`). Вкладка хранится в `?tab=`, `?customer=<id>` открывает карточку клиента. Ссылка «Управление» в шапке и в кабинете показывается при любом праве.

## Как включить доступ сотруднику

1. Администратор открывает `/admin` → «Команда», вводит имя, рабочий email и роль, ставит статус **«Активен — доступ включён»** и сохраняет. Доступ действует сразу, без перезапуска.
2. Сотрудник открывает Atlas, входит **по коду на этот email или через Google с этим адресом**, затем нажимает «Управление» в шапке. При первом входе создаётся обычный аккаунт покупателя; права добавляются к нему.
3. Чтобы отключить — статус «Отключён». Права пропадают при следующем запросе к API (`/api/account` перечитывает роль при каждом обращении).

Каждое действие сотрудника записывается в журнал (`market_audit_events`) с `actor_email` сотрудника — тем адресом, которым он вошёл.

## Ограничения и что ещё не сделано

- Отдельных прав внутри очереди заказов нет: любой с `operations.read` видит все заказы и профили клиентов (включая адреса и телефоны). Сужение данных для support/warehouse — отдельная задача.
- `app/api/finance/route.ts` пока проверяет только основного администратора (`operator()`); роль `finance` заработает после замены на `requirePermission(user,'finance.read' | 'finance.write')` (см. followups координатору).
- `app/order-workspace.tsx` (очередь `/operations`) и `app/prelaunch-views.tsx` (`/analytics`) ещё проверяют `user?.operator`; для сотрудников без роли admin их нужно перевести на `user?.permissions?.includes('operations.read' | 'finance.read')`.
- Данные ответа `GET /api/operations` для роли support/finance по-прежнему содержат полные документы аккаунтов (они нужны для очереди); фильтрация полей по ролям не делалась.
- Регистрация вида «кто вошёл с какой ролью» в самой сессии не хранится: роль пересчитывается при каждом запросе — это намеренно, чтобы отключение действовало немедленно.
